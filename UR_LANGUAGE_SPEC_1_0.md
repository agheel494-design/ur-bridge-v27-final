# UR Language Specification 1.0

**Status:** Draft — awaiting ratification before Lexer implementation begins
**Author:** Aqeel (language designer)
**Scope:** This document is the sole authoritative source for Lexer, Parser, and AST
design. No compiler stage may be implemented without a corresponding section
in this specification. Any ambiguity encountered during implementation must be
resolved here first, not in code.

---

## 1. Core Design Philosophy

1. **Natural language proximity.** UR programs read like structured prose.
   Punctuation is minimized. Braces `{}` are never required for blocks —
   indentation communicates structure; `نهاية` / `end` marks explicit closure.

2. **True multilingualism.** Arabic and English (and future languages) are
   first-class surface representations of the *same* language. They produce
   identical ASTs. The compiler has no preferred language; a source file may
   mix keywords from any supported surface language freely.

3. **Canonical tokens, not reserved words.** The Lexer maps every surface-language
   keyword to a canonical internal token (e.g. `FUNCTION_KW`). Adding a new
   surface language means adding mappings — it never requires modifying the
   Parser or AST.

4. **Two-tier type system.** High-level types for readability (`عدد`, `int`);
   ABI-precise types for FFI correctness (`i32`, `u64`). Both live in the same
   type lattice.

5. **Expression-based semantics.** `if`/`إذا` produces a value when used in an
   expression context, and is a statement when its value is discarded. No special
   syntax distinguishes the two uses — context determines semantics.

6. **FFI is invisible to the end user (design intent).** Native library
   bindings are intended to appear as ordinary modules, generated by a
   binding generator rather than hand-written by the programmer.
   **Current implementation status, confirmed via direct inspection
   and per independent review**: this generator
   (`emitUrBindings()` in `src/ffi/bindgen/emitter.ts`) exists and is
   unit-tested at the level of producing UR-looking source text, but
   there is no confirmed, tested path from that generated text to an
   actually-callable, functioning binding — no public UR-language
   keyword, function, or syntax (`call_external` or any equivalent)
   currently exists for a UR program to invoke native/FFI
   functionality. **FFI/FRI is therefore not a usable feature of UR
   1.0 today** — it is documented here as design intent and a
   planned future feature, not as something a UR 1.0 program can
   rely on. See `docs/architecture/FFI_STATUS.md` for the full
   finding.

## 2. Source File Encoding

- Encoding: UTF-8, no BOM.
- Line endings: LF (`\n`) or CRLF (`\r\n`); the Lexer normalizes both to LF.
- File extension: `.ur`
- Identifiers: any Unicode letter or digit sequence (including Arabic script,
  CJK, Latin) starting with a letter or `_`. Digit-only identifiers are not
  permitted.

## 3. Canonical Token Table

Every keyword in every supported surface language maps to exactly one canonical
token. The Parser and all downstream stages see only canonical tokens.

### 3.1 Declaration keywords

| Canonical Token   | English surface      | Arabic surface     | Notes |
|-------------------|----------------------|--------------------|-------|
| `FUNCTION_KW`     | `function`, `func`   | `دالة`             |       |
| `LET_KW`          | `let`, `var`         | `عرف`, `دع`        |       |
| `TYPE_KW`         | `type`               | `نوع`              |       |
| `IMPORT_KW`       | `import`             | `استورد`           |       |
| `RETURN_KW`       | `return`             | `أرجع`             |       |
| `END_KW`          | `end`                | `نهاية`            | unified block terminator — see §3.5 |

### 3.5 Unified block terminator (confirmed design decision)

`END_KW` / `نهاية` closes ALL block types: functions, `if`, `else`, `while`,
`for`, and any future block construct. There is no `endif`, `endwhile`,
`endfn`, or similar variant — ever.

The Lexer emits a single `END_KW` token regardless of which block it closes.
The Parser maintains a **Block Stack** and determines which open block is
closed by matching the top of the stack. The Lexer has zero knowledge of
block structure — this separation is intentional and must be preserved.

**Consequence for extensibility:** adding new block types in the future
requires zero changes to the Lexer. Only the Parser's block-stack logic
is updated.

### 3.2 Control flow keywords

| Canonical Token   | English surface  | Arabic surface   |
|-------------------|------------------|------------------|
| `IF_KW`           | `if`             | `إذا`            |
| `ELSE_KW`         | `else`           | `وإلا`           |
| `WHILE_KW`        | `while`          | `بينما`          |
| `FOR_KW`          | `for`            | `لكل`            |
| `BREAK_KW`        | `break`          | `اكسر`           |
| `CONTINUE_KW`     | `continue`       | `تابع`           |

### 3.3 Literal keywords

| Canonical Token   | English surface  | Arabic surface   | Value |
|-------------------|------------------|------------------|-------|
| `TRUE_LIT`        | `true`           | `صحيح`           | boolean true |
| `FALSE_LIT`       | `false`          | `خطأ`            | boolean false |
| `NULL_LIT`        | `null`           | `لاشيء`          | null / nothing |

### 3.4 Operators and punctuation

These are language-universal (no surface variation):

| Token         | Surface  | Meaning |
|---------------|----------|---------|
| `PLUS`        | `+`      | add |
| `MINUS`       | `-`      | subtract / negate |
| `STAR`        | `*`      | multiply |
| `SLASH`       | `/`      | divide |
| `PERCENT`     | `%`      | modulo |
| `EQ`          | `=`      | assignment |
| `EQ_EQ`       | `==`     | equality |
| `BANG_EQ`     | `!=`     | inequality |
| `LT`          | `<`      | less than |
| `LT_EQ`       | `<=`     | less-or-equal |
| `GT`          | `>`      | greater than |
| `GT_EQ`       | `>=`     | greater-or-equal |
| `AND`         | `&&`     | logical and |
| `OR`          | `\|\|`   | logical or |
| `BANG`        | `!`      | logical not |
| `DOT`         | `.`      | member access |
| `COMMA`       | `،` `,` | separator (Arabic or Latin comma) |
| `COLON`       | `:`      | type annotation |
| `LPAREN`      | `(`      | open group |
| `RPAREN`      | `)`      | close group |
| `LBRACKET`    | `[`      | open index |
| `RBRACKET`    | `]`      | close index |
| `NEWLINE`     | `\n`     | statement separator (significant) |
| `EOF`         | —        | end of input |

## 4. Lexical Rules

### 4.1 Whitespace and newlines

- Spaces and tabs are insignificant within a line (they separate tokens).
- **Newlines are significant** — they act as statement separators (`NEWLINE`
  token). The Parser may consume consecutive newlines as one.
- A line whose only non-whitespace content is a comment produces no `NEWLINE`.

### 4.2 Comments

```
// This is a line comment (English)
// هذا تعليق سطري (Arabic)
/* block comment */
```

Block comments may not be nested. Comments produce no tokens.

### 4.3 Identifiers

```
IDENTIFIER := (LETTER | '_') (LETTER | DIGIT | '_')*
LETTER     := any Unicode letter (Lu, Ll, Lt, Lm, Lo categories)
DIGIT      := '0'..'9'
```

Identifiers are case-sensitive. `add` ≠ `Add`. Arabic identifiers follow the
same rule: `اجمع` is a valid identifier.

Keyword recognition: after tokenizing an identifier, the Lexer checks the
canonical keyword table. If a match is found, the keyword token is emitted
instead of `IDENTIFIER`. This lookup must be O(1) (hash table).

### 4.4 Integer literals

```
INT_LIT := DIGIT+
         | '0x' HEX_DIGIT+
         | '0b' BIN_DIGIT+
```

Underscores are allowed as visual separators and are ignored: `1_000_000`.

### 4.5 Float literals

```
FLOAT_LIT := DIGIT+ '.' DIGIT* EXPONENT?
           | DIGIT+ EXPONENT
EXPONENT  := ('e' | 'E') ('+' | '-')? DIGIT+
```

### 4.6 String literals

```
STRING_LIT := '"' (CHAR | ESCAPE)* '"'
ESCAPE     := '\n' | '\t' | '\r' | '\\' | '\"' | '\u{' HEX_DIGIT+ '}'
```

Strings are UTF-8. Multi-line strings use `\n` or a backslash continuation
at end-of-line.

### 4.7 Lexer error recovery

On an unrecognized character, the Lexer emits an `ERROR` token containing
the offending character and advances by one code point. Lexing continues.
Errors are collected and reported after the full file is lexed — the Lexer
does not abort on first error.

## 5. Syntax (Grammar)

The grammar uses EBNF notation. `?` = optional, `*` = zero or more, `+` = one
or more, `|` = alternative.

### 5.1 Top-level structure

```
program        := statement* EOF

statement      := import_stmt
               | function_decl
               | type_decl
               | let_stmt
               | return_stmt
               | if_stmt
               | while_stmt
               | for_stmt
               | expr_stmt
               | NEWLINE
```

### 5.2 Import statement

```
import_stmt    := IMPORT_KW module_path NEWLINE
module_path    := IDENTIFIER (DOT IDENTIFIER)*
```

Examples:
```
import math
استورد sqlite
import std.collections
```

### 5.3 Function declaration

```
function_decl  := FUNCTION_KW IDENTIFIER LPAREN param_list? RPAREN
                  (COLON type_expr)?
                  NEWLINE
                  statement*
                  END_KW NEWLINE

param_list     := param (COMMA param)*
param          := IDENTIFIER (COLON type_expr)?
```

Examples:
```
function add(a, b)
    return a + b
end

دالة اجمع(أ: عدد، ب: عدد): عدد
    أرجع أ + ب
نهاية
```

### 5.4 Let statement

```
let_stmt       := LET_KW IDENTIFIER (COLON type_expr)? EQ expr NEWLINE
```

Examples:
```
let x = 42
عرف اسم: نص = "عقيل"
دع نتيجة = اجمع(5، 7)
```

### 5.5 Return statement

```
return_stmt    := RETURN_KW expr? NEWLINE
```

### 5.6 If expression / statement

`if` is an expression when it appears on the right side of an assignment or
as a function argument. It is a statement when its value is discarded.

```
if_expr        := IF_KW expr NEWLINE
                  statement*
                  (ELSE_KW NEWLINE statement*)?
                  END_KW

if_stmt        := if_expr NEWLINE
```

The value of an `if` expression is the value of the last expression in the
taken branch. If `else` is absent and no branch is taken, the value is `null`.

Examples:
```
// Statement form
if age >= 18
    print("adult")
else
    print("minor")
end

// Expression form
let label = if age >= 18
    "adult"
else
    "minor"
end

// Arabic expression form
دع التصنيف =
    إذا العمر >= 18
        "بالغ"
    وإلا
        "قاصر"
    نهاية
```

### 5.7 While loop

```
while_stmt     := WHILE_KW expr NEWLINE
                  statement*
                  END_KW NEWLINE
```

### 5.8 For loop

```
for_stmt       := FOR_KW IDENTIFIER IN_KW expr NEWLINE
                  statement*
                  END_KW NEWLINE

IN_KW          := 'in' | 'في'   // contextual — not a reserved word
```

`in` / `في` is recognized contextually inside `for` — it is not a global
reserved word and may be used as an identifier elsewhere.

### 5.9 Expressions

```
expr           := assignment_expr

assignment_expr:= IDENTIFIER EQ expr
               | logic_or_expr

logic_or_expr  := logic_and_expr (OR logic_and_expr)*
logic_and_expr := equality_expr  (AND equality_expr)*
equality_expr  := relational_expr ((EQ_EQ | BANG_EQ) relational_expr)*
relational_expr:= additive_expr  ((LT | LT_EQ | GT | GT_EQ) additive_expr)*
additive_expr  := mult_expr      ((PLUS | MINUS) mult_expr)*
mult_expr      := unary_expr     ((STAR | SLASH | PERCENT) unary_expr)*
unary_expr     := (BANG | MINUS) unary_expr
               | postfix_expr
postfix_expr   := primary_expr (call_suffix | index_suffix | member_suffix)*
call_suffix    := LPAREN arg_list? RPAREN
index_suffix   := LBRACKET expr RBRACKET
member_suffix  := DOT IDENTIFIER

primary_expr   := INT_LIT
               | FLOAT_LIT
               | STRING_LIT
               | TRUE_LIT | FALSE_LIT | NULL_LIT
               | IDENTIFIER
               | LPAREN expr RPAREN
               | if_expr

arg_list       := expr (COMMA expr)*
```

### 5.10 Type expressions

```
type_expr      := base_type
               | IDENTIFIER         // named / user-defined type

base_type      := 'عدد'   | 'int'   | 'i8'  | 'i16' | 'i32' | 'i64'
               | 'عشري'  | 'float' | 'f32' | 'f64'
               | 'منطقي' | 'bool'
               | 'نص'    | 'string'
               | 'حرف'   | 'char'
               | 'بايت'  | 'byte'  | 'u8'
               | 'u16'   | 'u32'   | 'u64'
               | 'لاشيء' | 'null'  | 'void'
```

### 5.11 Type declaration

```
type_decl      := TYPE_KW IDENTIFIER EQ type_body NEWLINE

type_body      := LBRACE field_list RBRACE   // struct-like (future, alternative syntax)
               | type_expr                   // alias
```

**Corrected, per direct inspection and live testing**: `struct`
declarations (using the `struct Name ... end` syntax already shown
in this document — not the `{}` form above, which remains a future,
alternative syntax) are fully supported and working in UR 1.0 today —
confirmed via live compilation through Lexer, Parser, Semantic
Analysis, and (as a value) Canonical IR. **`enum` is genuinely not
supported** — the Parser explicitly rejects it (`PE009`: "enum
declarations are not supported in UR 1.0. This feature is planned
for a future version"). The prior wording here ("full struct/enum
syntax is deferred to Specification 1.1") incorrectly grouped a
working feature (`struct`) together with a genuinely deferred one
(`enum`) — corrected to avoid overstating what is unsupported.

**A related, real, separate defect** (not a missing feature — logged
in `docs/architecture/COMPILER_BACKLOG.md`'s own Bug classification,
not fixed here): while `struct` *declarations* work with zero
errors, *using* a struct's own name as a variable or parameter type
fails at Type Checker (`TY1001: "unknown type"`). Struct declaration
and struct usage are not equally supported today, despite both being
part of the same feature.

## 6. Type System

### 6.1 Tier 1 — User-facing types

| UR type     | Arabic     | Meaning |
|-------------|------------|---------|
| `int`       | `عدد`      | Platform integer (64-bit on 64-bit targets) |
| `float`     | `عشري`     | Platform float (64-bit on 64-bit targets) |
| `bool`      | `منطقي`    | Boolean: `true`/`صحيح` or `false`/`خطأ` |
| `string`    | `نص`       | UTF-8 string |
| `char`      | `حرف`      | Unicode scalar value (U+0000..U+10FFFF) |
| `byte`      | `بايت`     | Unsigned 8-bit integer |
| `null`      | `لاشيء`    | Absence of value (type and value) |

### 6.2 Tier 2 — ABI-precise types

These map 1:1 to the ABI types defined in `src/ffi/abi/`. They are required
when interoperating with native libraries via UR-Bridge.

**(ADR-1, ratified): Tier 2 names are reserved exclusively for FFI/ABI
declarations and are not valid types for ordinary function signatures,
variable declarations, or any other general UR code — `function
add(a: i32, b: i32): i32` is not valid v1.0 UR. Use the Tier 1 `int`
type for general-purpose integer values instead.**

| UR type | ABI equivalent | Notes |
|---------|---------------|-------|
| `i8`    | `i8`          | signed 8-bit |
| `i16`   | `i16`         | signed 16-bit |
| `i32`   | `i32`         | signed 32-bit |
| `i64`   | `i64`         | signed 64-bit |
| `u8`    | `u8`          | unsigned 8-bit |
| `u16`   | `u16`         | unsigned 16-bit |
| `u32`   | `u32`         | unsigned 32-bit |
| `u64`   | `u64`         | unsigned 64-bit |
| `f32`   | `f32`         | 32-bit float |
| `f64`   | `f64`         | 64-bit float |
| `void`  | —             | no value (function return only) |

### 6.3 Type inference

Type annotations are optional. The compiler infers types from the right-hand
side of `let` declarations and from function return expressions. Explicit
annotations take precedence and are checked for consistency.

### 6.4 Tier mapping

`int` maps to `i64` on 64-bit targets. `float` maps to `f64`.
`byte` maps to `u8`. These mappings are part of the target specification
and are not user-configurable in Specification 1.0.

## 7. Module System

### 7.1 Import semantics

`import math` makes the name `math` available as a module identifier.
Members are accessed with `.`: `math.sqrt(x)`.

The module resolution order is:
1. Standard library modules (built-in)
2. urpm-installed packages (`packages/`)
3. Relative file paths (`./`, `../`)
4. Native bindings registered with Platform SDK

### 7.2 Native bindings — user-facing model

A native library bound via UR-Bridge is imported identically to a source module:

```
import sqlite

let db = sqlite.open(":memory:")
```

The Binding Generator (already implemented in `src/ffi/bindgen/`) produces a
UR module wrapper automatically. The programmer never writes `extern`, `native`,
or FFI-specific syntax unless they are *authoring* a binding.

The module name (`sqlite`) is the `name` field from the driver's
`NativeLibraryDescriptor`. Platform SDK resolution is transparent.

## 8. Program Structure Example

Full reference program in Arabic:

```ur
استورد حساب

دالة رئيسية()
    عرف أ: عدد = 5
    عرف ب: عدد = 7
    عرف نتيجة = حساب.اجمع(أ، ب)
    اطبع(نتيجة)

    دع تصنيف =
        إذا نتيجة > 10
            "كبير"
        وإلا
            "صغير"
        نهاية

    اطبع(تصنيف)
نهاية
```

Identical program in English:

```ur
import math

function main()
    let a: int = 5
    let b: int = 7
    let result = math.add(a, b)
    print(result)

    let label =
        if result > 10
            "large"
        else
            "small"
        end

    print(label)
end
```

Both compile to the same AST.

## 9. AST Node Catalog

The AST is the single representation that all downstream stages (Semantic,
Type System, Module System, Code Generator) consume. It is language-agnostic
— no surface-language information survives past the Parser.

### 9.1 Program node

```
Program {
  body: Statement[]
  source: string       // file path, for diagnostics
}
```

### 9.2 Statement nodes

```
ImportStatement {
  path: string[]       // ["math"] or ["std", "collections"]
  span: Span
}

FunctionDeclaration {
  name: string
  params: Parameter[]
  returnType: TypeExpr | null
  body: Statement[]
  span: Span
}

Parameter {
  name: string
  typeAnnotation: TypeExpr | null
  span: Span
}

LetStatement {
  name: string
  typeAnnotation: TypeExpr | null
  value: Expression
  span: Span
}

ReturnStatement {
  value: Expression | null
  span: Span
}

ExpressionStatement {
  expression: Expression
  span: Span
}
```

### 9.3 Expression nodes

```
IfExpression {
  condition: Expression
  thenBranch: Statement[]
  elseBranch: Statement[] | null
  span: Span
}

WhileStatement {
  condition: Expression
  body: Statement[]
  span: Span
}

ForStatement {
  variable: string
  iterable: Expression
  body: Statement[]
  span: Span
}

BinaryExpression {
  operator: BinaryOp
  left: Expression
  right: Expression
  span: Span
}

UnaryExpression {
  operator: UnaryOp
  operand: Expression
  span: Span
}

CallExpression {
  callee: Expression
  arguments: Expression[]
  span: Span
}

MemberExpression {
  object: Expression
  property: string
  span: Span
}

IndexExpression {
  object: Expression
  index: Expression
  span: Span
}

AssignmentExpression {
  target: string
  value: Expression
  span: Span
}

Identifier {
  name: string
  span: Span
}

IntLiteral     { value: bigint;  span: Span }
FloatLiteral   { value: number;  span: Span }
StringLiteral  { value: string;  span: Span }
BoolLiteral    { value: boolean; span: Span }
NullLiteral    {                 span: Span }
```

### 9.4 Type expression nodes

```
NamedType {
  name: string          // canonical name ("int", "i32", "عدد" → "int")
  span: Span
}
```

Type canonicalization: `عدد` → `int`, `منطقي` → `bool`, etc.
This happens during AST construction (in the Parser), not in a separate pass.

### 9.5 Operator enums

```
BinaryOp = ADD | SUB | MUL | DIV | MOD
         | EQ | NEQ | LT | LTE | GT | GTE
         | AND | OR

UnaryOp  = NEG | NOT
```

### 9.6 Span

```
Span {
  file: string
  startLine: number    // 1-based
  startCol:  number    // 1-based, code-point offset
  endLine:   number
  endCol:    number
}
```

All AST nodes carry a `Span`. No exceptions — this is required for
diagnostic quality and LSP support.

## 10. Error Codes

### 10.1 Lexer errors (LE prefix)

| Code  | Meaning |
|-------|---------|
| LE001 | Unrecognized character |
| LE002 | Unterminated string or char literal |
| LE003 | Invalid Unicode escape sequence |
| LE004 | Invalid numeric literal |
| LE005 | Char literal does not contain exactly one character (empty or multi-character) |

### 10.2 Parser errors (PE prefix)

| Code  | Meaning |
|-------|---------|
| PE001 | Expected expression, got `<token>` |
| PE002 | Expected `END_KW` / `نهاية`, got `<token>` |
| PE003 | Expected a specific punctuation token (`)`, `]`, `:`, `=`, `(`), got `<token>` |
| PE004 | Unexpected token `<token>` at top level |
| PE005 | Expected identifier after a declaration keyword (`function`/`let`/`struct`/`type`) |
| PE006 | Expected identifier after `LET_KW` |
| PE007 | Expected `=` after identifier in let statement |
| PE008 | Struct-like `type NAME = { ... }` body used — deferred to Specification 1.1 (§11); only `type NAME = <type>` aliases are valid in v1.0 |
| PE009 | `enum` declaration attempted — not supported in UR 1.0, planned for a future version (per FINAL_CONSISTENCY_REVIEW.md's finding: `enum` is not yet a reserved keyword; this diagnostic exists specifically to prevent silent, meaningless acceptance of `enum` syntax) |
| PE010 | An unrecognized modifier keyword (e.g. `async`, `const`, `static`, `public`, `export`, `abstract`) immediately preceding `function`/`struct`/`type` — UR 1.0 declarations do not support modifiers. One general check (found during Compiler Stabilization Sprint's systematic scan for the same silent-success pattern PE009 addressed) covers this entire class, not one diagnostic per keyword. |

## 11. What This Specification Does NOT Cover (Deferred to 1.1)

The following are explicitly out of scope for the Lexer and Parser that
implement this spec. They must not be implemented before Specification 1.1
is ratified:

- **`for`/`in` RANGE loops specifically** (`for i in 1 to 5` — a range
  expression as the iterable; §5.8's grammar remains recognized by the
  Parser for forward compatibility, but Lowering must continue to
  reject it — per `UR_LANGUAGE_VERSION_MATRIX.md`, ratified during UR
  Language Freeze Week: a genuinely new CFG shape, not a small patch.)
  **[V1.0-FOR-IN-CONTRACT-INCLUSION-GATE-012 — CONTRACT CHANGE,
  APPROVED]**: `for`/`in` ARRAY ITERATION (`for x in arr`, a plain
  array variable as the iterable) is CONTRACTED for UR v1.0 — real,
  verified semantics (single/multiple elements, nested loops,
  loop-variable scope, mutation during iteration, `return`, `break`,
  `continue`) confirmed identical on the Interpreter and the C
  Backend, and protected by conformance/012-019_forin_*. WASM
  currently rejects array iteration (`[WASM1002] unsupported CFG
  shape`) — a real, general WASM control-flow limitation, not specific
  to `for`/`in` — WASM support is not required for this capability's
  own v1.0 contract status. Range iteration (above) remains excluded
  from v1.0 and deferred to 1.1; this change covers array iteration
  only.
- **`if` used as an expression** (§5.6's grammar remains recognized by
  the Parser, Lowering must continue to reject it — same reasoning
  and same ratification as `for` above.)
- **Named-type annotations** (using a `struct` or `type`-alias name as
  an explicit `: TypeName` annotation, e.g. `let p: Point = ...` or
  `let x: MyInt = ...` — inference from a constructor call, e.g. `let
  p = Point(1, 2)`, remains valid v1.0 code and is unaffected.)
- **Type inference for unannotated parameters/variables used in a
  context requiring a concrete backend type** (e.g. an unannotated
  parameter passed to `!`, or used in a multi-argument call without an
  explicit type — v1.0 requires an explicit annotation in these cases;
  full bidirectional/contextual inference is 1.1 scope.)
- **Enum declarations** (structs are already implemented and shipped
  — see LANGUAGE_SYNTAX_1_1_SPEC.md §2 — this bullet previously
  grouped them together incorrectly; corrected during UR Language
  Freeze Week)
- Generics / type parameters
- Pattern matching (`match` / `طابق`)
- Closures / anonymous functions
- Async / await
- Error handling (`try` / `catch`)
- Operator overloading
- Macros
- Multiple return values (tuples)
- Array and map literals (beyond simple indexing)

## 12. Compatibility with UR-Bridge v27-rc1

This specification is designed to integrate with the following already-frozen
components without modification:

| Component | Integration point |
|---|---|
| `src/compiler/incremental/` | The Lexer/Parser pipeline produces the `ArtifactSet` consumed by `IncrementalPipeline` |
| `src/ffi/abi/` | Tier-2 ABI types map 1:1 to `AbiPrimitiveType` in `types.ts` |
| `src/ffi/bindgen/` | `emitUrBindings()` already produces `.ur`-syntax output — the syntax in this spec is its target |
| `src/ffi/native/types.ts` | `NativeArg`/`NativeCallResult` kinds (`i32`, `i64`, `f64`, `str`, `ptr`) align with Tier-2 type names |
| `src/platform-sdk/` | `import sqlite` triggers `PlatformSDK.bindByCapability("database")` |
| `src/lsp/` | `Span` in every AST node maps directly to LSP `Position`/`Range` |

## 13. Implementation Order (mandated)

After this specification is ratified, implementation proceeds in this exact
order. No stage begins until the previous stage has passing tests:

1. **Lexer** — tokenizes UTF-8 source → `Token[]`, handles error recovery
2. **Parser** — tokens → AST, Pratt-style expression parsing, error recovery
3. **AST Printer** — for debugging and test assertions
4. **Semantic Analyzer** — name resolution, scope checking, basic type inference
5. **Type System** — full type inference + checking, tier-1 ↔ tier-2 mapping
6. **Module System** — import resolution, native binding wiring
7. **Pipeline integration** — connect to `IncrementalPipeline` and `FFI`

Each stage ships with: unit tests, integration tests, and at least one
regression test for each error code it produces.
